# Исследование алгоритмов прокладки кабеля

Дата обзора: 2026-10-25.

## Что применяют в похожих системах

### Дорожные графы

OSRM и GraphHopper используют подготовленный граф дорог, а не перебор геометрий при каждом запросе. Для ускорения применяются Contraction Hierarchies (CH), Multi-Level Dijkstra (MLD) и варианты A* с landmarks (ALT). Их сильная сторона — много быстрых запросов по стабильному графу. Они не решают автоматически нашу задачу: болота, озёра, здания, лес, поля, разрешённые переходы и инженерные штрафы должны остаться изменяемой частью стоимости.

Источники:

- [OSRM API](https://project-osrm.org/docs/v5.24.0/api/)
- [GraphHopper: Contraction Hierarchies](https://www.graphhopper.com/blog/2020/07/22/what-is-contraction-hierarchies/)
- [pgRouting concepts](https://docs.pgrouting.org/latest/en/pgRouting-concepts.html)
- [pgRouting pgr_dijkstra](https://docs.pgrouting.org/latest/en/pgr_dijkstra.html)

### Least-cost path в GIS

GRASS GIS `r.cost` строит растр накопленной стоимости от исходных ячеек, а `r.drain` восстанавливает путь по этому полю. Такой подход хорошо подходит для стоимости землепользования и рельефа, но разрешение напрямую определяет точность и память. В кабельном проекте растр должен быть только грубым этапом, а итоговый коридор — перепроверяться по исходным векторным геометриям.

Источники:

- [GRASS r.cost](https://grass.osgeo.org/grass-stable/manuals/r.cost.html)
- [GRASS r.drain](https://grass.osgeo.org/grass-stable/manuals/r.drain.html)

## Что это означает для приложения

Текущий `GridRoutePlanner` уже делает полезные вещи: локальную метрическую проекцию, A*, пространственный STRtree, кеш рёбер, отдельные профили стоимости и проверку каждого итогового сегмента. Главный недостаток — область и сетка выбираются сразу для всего прямоугольника между точками. Поэтому плотность сетки и количество геометрий растут вместе с расстоянием, хотя большая часть страны не является реальным коридором поиска.

Рекомендуемая архитектура следующего этапа:

1. Подготовить для страны иерархические тайлы: обзорный слой, региональный слой и локальные исходные геометрии. В каждом тайле хранить R-tree и упрощённые препятствия только для поиска, а не для финальной проверки.
2. На обзорном уровне искать несколько кандидатов коридора крупной ячейкой или графом проходимых областей. Ячейка должна быть консервативной: если в ней есть блокирующее препятствие, она не должна становиться свободной из-за упрощения.
3. Расширить найденный коридор на запас и выполнить точный A* только внутри полосы. Если путь не найден, автоматически расширять полосу в 2 раза; это безопаснее искусственного лимита расстояния и обычно дешевле полного прямоугольника.
4. На локальном уровне использовать vector visibility/portal graph для вершин препятствий, мостов и точек входа в тайлы. Это уменьшит ступенчатость raster-маршрута и позволит контролировать точность возле узких проходов.
5. Разделить стоимость на жёсткие запреты и мягкие критерии. Сначала исключаются вода без перехода, здания и болота; затем оптимизируется взвешенная функция длины, леса, поля, дорог, просек, числа переходов и инженерных штрафов. Весы должны быть видны пользователю и сохраняться вместе с результатом.
6. Для нескольких точек сначала строить последовательные legs, как сейчас. Если появится задача подключить много абонентов одной сетью, это уже не один shortest path, а Steiner tree/сетевой дизайн; её нельзя незаметно подменять последовательным A*.

## Приоритеты реализации

1. Довести тайловую загрузку карты и LOD до стабильного бюджета объектов на Android.
2. Добавить адаптивный corridor search с повторным расширением и тестами на узкий мост, реку и обход препятствия.
3. Подготовить benchmark-пакет: Минск–областной центр, короткий городской маршрут, маршрут через мост, маршрут с обходом озера. Для каждого фиксировать время SQLite, подготовки индекса, поиска, число узлов, объём памяти и отклонение длины от точного локального решения.
4. Только после benchmark заменить равномерную сетку на иерархический граф. CH/MLD имеет смысл лишь для стабильного дорожного подграфа; применять его ко всем инженерным ограничениям нельзя.

## Критерии точности

Быстрее не означает точнее. Каждый кандидат должен сохранять исходные координаты точек, не пересекать блокирующие геометрии, проверять весь сегмент, явно отмечать OSM-кандидаты мостов как непроверенные и показывать длину, стоимость и использованные допущения. Изменение размера ячейки должно сравниваться с эталонным локальным расчётом, иначе ускорение может незаметно открыть препятствие.
