# Воспроизводимость поиска и разбор отказов

Расширенный корпус Беларуси, отдельная отложенная выборка и агрегированная
классификация описаны в [исследовании качества маршрутизации](routing-quality-research.md).
Они дополняют приведённые ниже исходные 88 регрессий и отдельные контроли.

Проверка маршрутизации должна отличать потерю известного допустимого пути, нарушение предметных правил и исследовательский случай без подтверждённого обхода. Общая доля `success` не является процентом исправности алгоритма: часть входных пар может требовать запрещённого перехода.

## Правила этой работы

Пересечение существующих дорог, включая `track`, `service` и `unclassified`, сохраняет прежние Domain-ограничения. `service` обозначает подъездные и внутренние дороги — к зданиям, парковкам, предприятиям; это не характеристика покрытия. Возможность прокладки через грунтовку и отражение такого пересечения в статистике приложения требуют отдельного изменения модели. `unclassified` не получает нового разрешения.

`highway=proposed` обозначает запланированную дорогу, строительство которой ещё не началось ([описание OSM](https://wiki.openstreetmap.org/wiki/Tag:highway=proposed)). Импорт не создаёт из этого тега существующий Road или BridgeCandidate. Независимые физические теги того же объекта продолжают классифицироваться: например, вода, здание или существующая железная дорога. Дорога на стадии `construction` этим исправлением не исключается.

## Подтверждённый пропуск пути

Ранее пользовательская точка соединялась только с ближайшими узлами регулярной сетки. Даже существование допустимого моста рядом не помогало, если узкий подход не содержал узлов сетки. Пример регрессии: коридор шириной 4 м между зданиями и сетка 20 м; независимо проверенная ломаная ведёт от точки к входу изогнутого моста, но прежний граф возвращает `GridConnectionUnavailable`.

Если у начальной или конечной точки нет исходных допустимых соединений с регулярной сеткой, исправление подключает её непосредственно к допустимым входам переходов в том же ограниченном соседстве. Каждый соединитель проходит полную обычную проверку препятствий; внутренний узел подземной сети без подтверждённого выхода не становится наземным входом. Промежуточные точки проверочного пути не передаются планировщику. Подключение к изолированной компоненте сетки вместо нужного входа остаётся отдельным неисследованным случаем; это исправление не обещает полноту поиска.

## Реальные отказы исходного набора

Исходный корпус `samples/routing-crossing-mass-v1.json` содержит 88 пар и сохраняется без перегенерации. Предыдущее измерение на `23adea9` и пакете PR #59: 32 допустимых маршрута, 56 `NoRouteInSearchArea`.

Независимая проверка прямых A–B для всех 56 отказов выявила недопустимый дорожный контакт в каждом случае; дополнительно 34 прямые пересекают воду без допустимого перехода, 21 — здания, 7 — болота. Группы пересекаются. Проверены исходные теги 296 дорожных объектов. В семи случаях прямую блокируют только дороги типов `track`, `service` или `unclassified`; это группа для предметного обследования, а не доказательство возможности прокладки.

Для `mass-naliboki-bridge-01` и `mass-smolevichi-bridge-03` дополнительные запуски с запросом шага 5 м и лимитом 500000 узлов также вернули `NoRouteInSearchArea`. Ранее исследованные ломаные через мостовые кандидаты нарушали проверку других дорог, воды или болот ([разбор PR #53](evidence/routing-pr53/report.md)). Эти факты не доказывают отсутствия иного допустимого обхода. Они также не позволяют объявить все 56 отказов одним исправленным дефектом.

В `mass-vitebsk-bridge-04` дополнительно обнаружен `way/327549917`, ошибочно импортированный как Road при `highway=proposed`. После исправления этого источника остаются другие существующие дороги; ожидаемый успех данного сценария не назначается без полного проверенного пути.

## Автоматическая приёмка

Основной корпус используется как неизменяемая группа сравнения. Отдельные положительные контроли должны доказанно проходить и использовать нужный переход; отрицательные контроли выключают подземное разрешение. Критерии провала проверки: техническая ошибка или таймаут, неполный результат, недопустимая геометрия, потеря известного допустимого пути либо несовпадение происхождения данных. Исследовательский `NoRoute` сохраняется вместе с причиной и не считается доказанным физическим запретом.

Пакет получает существующий инструмент подготовки страны из закреплённого PBF; проверяются manifest и SHA-256. Зависимость от короткоживущего transport artifact и количества ровно 444 подземных кандидатов удаляется. Аудит современных подземных сетей объединяет только явную принадлежность компоненте из исходных OSM node IDs.

Структурированная диагностика Verify сохраняет фактический шаг и размеры сетки, границы поиска, подключение концов и порталов и исход каждого поискового участка, включая неуспешный. Она помогает локализовать потерю соединения, но не превращает отсутствие результата конечного графа в доказательство отсутствия пути на местности.

## Запуск

Метка PR `ci:routing-crossing-pilot` включает полный автоматический прогон; новые коммиты в помеченном PR повторяют проверку. Ручной запуск workflow принимает необязательный `baseline_ref`. При сравнении обе версии Verify используют одну и ту же базу; исходные 88 точек и настройки не перегенерируются. Отдельные контроли включают и выключают подземные переходы явно. Настройки приложения включают их принудительно, тогда как низкоуровневый `RoutingOptions` по умолчанию оставляет флаг выключенным; фактические параметры сохраняются в отчёте.

После штатного получения и распаковки актуального пакета из корня репозитория:

```powershell
uv run --project tools/GeodataPreparation --locked python tools/routing_regression.py --data artifacts/belarus --verify-dll tools/CableRoutePlanner.Verify/bin/Release/net8.0/CableRoutePlanner.Verify.dll --output artifacts/routing-regression
uv run --project tools/GeodataPreparation --locked python tools/routing_portal_witnesses.py --data artifacts/belarus --output artifacts/routing-regression/portal-witnesses.json
```

`--baseline-verify-dll` и `--baseline-source` задают собранный исходный вариант для сравнения на том же пакете. По умолчанию одновременно работает один ограниченный процесс. Для мощной локальной машины можно явно передать `--workers 8`; каждый процесс получает лимит managed heap 1536 MiB, SQLite открывается отдельно только для чтения. Параллельные времена не сравниваются с последовательными замерами.

Итоги `results.json` и `summary.md`, исходные параметры, сырые результаты, stdout/stderr и диагностика каждого сценария сохраняются в артефакте workflow. Успешные контроли проверяют фактическую геометрию, ограничения длины, исходные узлы подземной сети и нужный вид перехода. Сохранённый пример у пешеходного моста Пролетарской является smoke-проверкой построения рядом с объектом; прохождение именно мостового перехода доказывает отдельный непрямой сценарий Смолевичей. Дополнительные проверенные ломаные через три выбранных моста сопоставляются с результатами поиска: допустимый путь внутри фактической области поиска не может остаться незамеченным при `NoRoute`. Путь за границами этой области сохраняется как отдельное ограничение исследования.

Сам аудитор также имеет регрессии: два законных пересечения одного водного объекта через разные мосты должны приниматься, а отсутствие второго перехода — отклоняться. Проверка не принимает незаполненную диагностику как успешное свидетельство и повторно сверяет входные файлы и бинарники после выполнения.
