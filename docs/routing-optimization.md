# Оптимизация поиска

Подготовка находится в Infrastructure, правила стоимости — в Domain, UI не хранит GIS-индексы. PreparedRoutingAreaCache хранит только последнюю расчётную область для одного экземпляра репозитория. Ключ включает точные границы и размер ячейки; пакет репозитория неизменяем в течение жизни планировщика. При замене пакета нужно создать новый репозиторий и планировщик. Память не растёт с числом запросов. Отменённая или неудачная подготовка не заменяет успешную запись. Сам поиск и проверка сегментов продолжают выполняться заново.

Логи отдельно показывают запрос SQLite, WKB/проекцию/STRtree и последующий расчёт. Нулевые времена подготовки при повторе обозначают повторное использование. Индекс не кэшируется для всей Беларуси: это потребовало бы слишком много памяти телефона.

Иерархический поиск и точный SQL-фильтр по прямой пока не включены: прямой коридор может исключить единственный мост или необходимый обход. Нужны сравнение с полным поиском и сценарии узких проходов. Сначала следует измерить холодный и повторный расчёты на устройстве.

DEM нельзя заменить эвристическими высотами: нужен проверенный локальный источник высот с лицензией, покрытием и обработкой отсутствующих значений. Пока подъём остаётся неизвестным. Неоднородная сетка и векторные мостовые рёбра требуют отдельного графа с сохранением проверки всех сегментов; существующее выравнивание геометрии моста остаётся действующим.

Контрольный локальный прогон по Минску (53.9490,27.5180 → 53.9500,27.5190, Linux под strace) до уточнения эвристики: SQLite 86 мс, подготовка 97 мс, расчёт 2171 мс, 656 проверенных рёбер. Это единичный замер, не прогноз для Android.
