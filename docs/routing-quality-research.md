# Исследование качества маршрутизации Беларуси

Инфраструктура расширяет существующие `routing_regression`, `routing_recovery`,
`routing_portal_witnesses` и независимый `independent_probe`. Алгоритм маршрутизации
и предметные правила в этой работе не меняются. Исходная точка — main после PR #64.

## Корпус и отложенная оценка

`samples/routing-crossing-mass-v1.json` сохраняется побайтно: те же 88 пар,
настройки, контроли и методика проверки. Новый `samples/routing-research-v1.json`
добавляет 212 сценариев: 170 для исследования и 42 для отложенной оценки.
Шесть существующих контролей выполняются отдельно и не входят в знаменатель 300.

Генератор `tools/routing_research_corpus.py` читает закреплённый PBF, проверяет его
SHA-256 и текущий рецепт подготовки SQLite. Он использует реальные OSM ID, теги,
административные границы всех областей и Минска, фиксированный seed `20261127`,
устойчивый порядок кандидатов, квоты категорий и диапазоны расстояний. Проверки
плотности зданий и узких промежутков используют геометрию. Коридоры разделяются
пространственно; отложенные коридоры отделены и от исходных 88 сценариев.
Нехватка категории или противоречие данных завершают генерацию ошибкой.

Генератор не вызывает маршрутизатор и не использует результаты эксперимента.
Корпус и квитанция генерации фиксируются **до** запуска Verify. Изменение корпуса
требует новой версии и отдельного описания методики, а не отбора удобных исходов.
Состав категорий и фактические квоты находятся в квитанции генерации.

По умолчанию исследовательский запуск исключает 42 отложенных случая.
`--evaluate-holdout` разрешает отдельную оценку. Их индивидуальные результаты
попадают только в отдельный `sealed-holdout` artifact; автоматический backlog,
частоты приоритизации и репрезентативные примеры используют только исходную и
исследовательскую выборки. **Не используйте отложенные геометрии, отказы и логи
для разработки последующих исправлений.** Если это произошло, выборка больше
не является отложенной: необходима новая независимая версия.

## Интерпретация результатов

| Класс | Необходимое свидетельство |
| --- | --- |
| `valid_route` | Все возвращённые альтернативы прошли независимую проверку всей ломаной, концов, длины и разрешённых переходов |
| `invalid_route` | Хотя бы одна альтернатива имеет подтверждённое нарушение независимого аудита |
| `confirmed_missed_route` | При NoRoute существует отдельно проверенная допустимая ломаная с теми же входами и опциями внутри фактических границ поиска |
| `justified_refusal` | Независимо подтверждённый запрет размещения конкретной точки либо геодезическая нижняя граница длины превышает заданный максимум |
| `indeterminate` | Нет достаточного доказательства существования/отсутствия пути либо аудит результата неполон |
| `resource_limit` | Структурированное исчерпание поискового бюджета или фактический таймаут процесса |
| `technical_error` | Сбой процесса, повреждённый/неполный результат, противоречие входов или диагностических свидетельств |

NoRoute, исчерпанный конечный граф, раздельные консервативные компоненты и
заблокированная прямая A–B **не доказывают** невозможности обхода. Независимый
поиск также ограничен ресурсами; его лимит не превращается в лимит алгоритма.
Предложенный независимым поиском путь повторно проверяется штатным независимым
геометрическим аудитором. Неуспешные предложения сохраняются без вывода о
несуществовании других путей. OSM-мост остаётся кандидатом, а не инженерным
разрешением. Допустимость здесь означает соответствие текущей предметной модели.

Для новых исследовательских сценариев отдельно проверяется известная граница
водного аудитора: он связывает мост только с непосредственно пересечённым водным
объектом, тогда как текущая модель применяет разрешённый коридор моста ко всем
затронутым водным объектам. Независимое уточнение читает точный набор объектов
последней поисковой области, проверяет активацию коридора пересечением воды и
полное покрытие спорного участка. Порог берётся из текущего исходника модели.
Исходный аудит сохраняется. Даже при таком доказательстве результат остаётся
`indeterminate`, с отдельным подтверждённым фактом `auditor_model_rule_mismatch`;
другие нарушения продолжают давать `invalid_route`. Для нового водного finding
такой вывод требует непустого пересечения маршрута с остаточным водным препятствием
после вычитания всех разрешённых openings; неполная проверка даёт неопределённость.
Это ограничение исследовательской
проверки, а не доказанный дефект маршрутизации. Прежний аудитор и методика 88
сценариев не меняются.

Пересечение железнодорожных путей разрешено намеренно и не считается дефектом.
OSM `access`/`military` позволяют исследовать закрытые территории, но отдельного
запрета в текущей модели нет. Это подтверждённое ограничение модели, а не ошибка
маршрутизатора и не изменение правил в данном PR.

Группы имеют владельца (`algorithm`, `model`, `geodata`, `resource`, `technical`),
уровень уверенности и область применимости. Например, `direct_road_barrier` —
подтверждённый факт о прямой, но не установленная причина неудачи поиска обхода.
`grid_resolution_loss` и `crossing_geometry_or_mapping_gap` — гипотезы, пока не
получен соответствующий независимый свидетель. Один случай может иметь несколько
групп; их количества нельзя складывать как непересекающиеся доли отказов.

## Воспроизведение

Подготовка зависимостей, hooks и проверенной карты описана в
[development.md](development.md) и [ci-geodata.md](ci-geodata.md). Карта и PBF
остаются в `artifacts/` или внешнем каталоге, не в Git.

```powershell
uv sync --locked
uv run --locked pre-commit install
uv sync --project tools/GeodataPreparation --locked
uv run --project tools/GeodataPreparation --locked python tools/GeodataPreparation/country_data.py ensure --output artifacts/belarus
uv run --project tools/GeodataPreparation --locked python tools/ci/routing_pilot_ci.py extract-db --data artifacts/belarus
dotnet build tools/CableRoutePlanner.Verify -c Release -warnaserror -p:RestoreLockedMode=true
uv run --project tools/GeodataPreparation --locked python tools/routing_research.py --data artifacts/belarus --verify-dll tools/CableRoutePlanner.Verify/bin/Release/net8.0/CableRoutePlanner.Verify.dll --output artifacts/routing-research --workers 2
```

Для полного первоначального эксперимента добавьте `--evaluate-holdout`.
Сравнение с предыдущим полным артефактом: `--baseline-report <каталог>/results.json`.
Нужны `development-records.json`, `provenance.json`, `evidence-manifest.json` и
перечисленные в нём сырые файлы. Обычный запуск автоматически сравнивает только
открытые 258 сценариев, даже если baseline был полным: sealed-файлы не загружаются
и не читаются. Отдельный `nonHoldoutEffectiveOptionsSha256` связывает настройки
этих случаев и всех шести контролей (264 входа); исходный полный дайджест включает
306 входов. Сравнение остаётся строгим по настройкам и составу случаев.
Только для разрешённой отложенной оценки нужны также
каталоги `holdout/` и `sealed-holdout/`. Проверяются хеши,
полнота, одинаковые корпус/SQLite/настройки/бюджеты/параллелизм и состав случаев.
Различающиеся платформы или бюджеты не дают сопоставимого измерения времени.
Для разработки исправлений используйте текущий CI-baseline с дайджестом открытой
проекции. Исторический local8-снимок `faaa4dd` предшествует этому расширению
метаданных: его полная проверка доступна, но открытая проекция без дайджеста
намеренно отклоняется и не переключается на чтение holdout.

Основной JSON агрегирован; длинные списки исходников, бинарников и подробности
сценариев вынесены в отдельные файлы с SHA-256. Воспроизводимость включает хеш
реализации алгоритма отдельно от изменений исследовательской обвязки.
Различие байтового SQLite между ОС допустимо при одном закреплённом рецепте и
источнике; в рамках сравнения двух версий требуется одна и та же база.

## Измерения и CI

Каждая пара выполняется в холодном процессе. Wall time включает запуск и загрузку
данных; P95 интерполируется между упорядоченными измерениями. Verify измеряет
`PeakWorkingSet64` в байтах на момент окончания расчёта, до сериализации результата; для убитого процесса
память остаётся `null`, без подстановки нуля. Managed heap ограничен 1536 MiB;
это не ограничение всей RSS. Лимит процесса — 120 секунд. По умолчанию одновременно
работают два маршрутизатора; независимый ограниченный probe выполняется отдельно
с лимитом 30 секунд, 3000 объектов и 60000 исходных вершин. Его консервативный
поиск переиспользует существующую реализацию из recovery.

Fallback-статистика берётся из структурированных событий фактических попыток
сетки и surface recovery. Отсутствующие/усечённые события не считаются нулём.
Длины и стоимости сохраняются по именованным альтернативам; изменение стоимости
само по себе не доказывает изменение корректности или оптимальности.

Workflow **Belarus routing quality research** запускается отдельно вручную
либо меткой PR `ci:routing-research` (без отложенной оценки). Полный ручной запуск
требует `evaluate_holdout=true`. Параллелизм CI ограничен выбором 1/2, job —
120 минутами; устаревший запуск отменяется. Данные проходят существующий механизм
`country-data`. Все доступные свидетельства загружаются и при неуспешном запуске.
Существующий workflow исходных регрессий остаётся без изменений.

Для явной полной оценки ещё до объединения нового workflow в main предусмотрена
отдельная метка `ci:routing-research-evaluation`. Она включает 42 отложенных случая
и отдельный артефакт. Обычная исследовательская метка их не включает. Это также
позволяет проверить новый workflow в PR при ограничениях
[ручного запуска GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch).

Evidence gate требует полноты и неизменности входов, отсутствия технических ошибок
и успешной прежней регрессионной приёмки с recovery/portal-проверками. Отдельный
quality gate показывает новые недопустимые/пропущенные пути: они являются
результатом исследования и не препятствуют записи первого baseline. Сравнение
версий блокируется при потере ранее независимо подтверждённого допустимого пути.

Первый полный baseline и приоритеты последующих PR сохранены в
[компактном отчёте](evidence/routing-research-v1/report.md),
[агрегированном Markdown](evidence/routing-research-v1/baseline-local8.md) и
[JSON](evidence/routing-research-v1/baseline-local8.json). Последующие изменения алгоритма должны
проверять конкретный класс проблем на исследовательской выборке, добавлять
независимое доказательство регрессии и сохранять прежние предметные ограничения.
